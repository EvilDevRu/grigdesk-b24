# Стоковый Битрикс24 0.1.4

Внешний драйвер контракта 1 поддерживает два явно выбираемых способа подключения.
В настройках доски укажите HTTPS origin портала в baseUrl и выберите authMode.
После обновления с 0.1.0 способ подключения нужно выбрать и сохранить вручную.

## Токен доступа

Режим token предназначен для порталов с подпиской и доступом к REST.
В портале откройте «Разработчикам» → «Другое» → «Входящий вебхук»,
выдайте права на задачи, пользователей и группы и сохраните вебхук.
Из адреса вебхука `https://portal.example/rest/7/WEBHOOK_SECRET/` возьмите последний
секретный сегмент WEBHOOK_SECRET и укажите его в accessToken; baseUrl — только origin.
Доступность вебхуков и REST зависит от тарифа портала и прав пользователя.
Токен отправляется в теле POST, перенаправления и повторы запросов отключены.

## Логин и пароль

Режим password доступен для бесплатных порталов, где разрешён вход обычной формой
и сессионные REST-вызовы. Укажите login и password пользователя портала.
Порталы с обязательным внешним SSO или запретом сессионного REST так не подключаются.
Форма входа создаёт cookie-сессию. REST передаёт её куки и sessid (CSRF), а при
явном отказе сессии выполняет один вход и один повтор запроса с новым sessid.
Сетевая ошибка и обычный отказ в правах не повторяют мутацию.

Капча и 2FA немедленно возвращают «Требуется код/капча — войдите в портал и повторите».
Автоматического подбора кода и повторной отправки формы при таком ответе нет.
Куки хранятся в cookiePath host с правами 0600 и привязкой к реквизитам аккаунта.
Смена режима исключает реквизиты другого режима из REST-запроса.

## Возможности и проверки

Оба режима поддерживают чтение, создание, правку и завершение задач, комментарии,
пользователей и проекты. capabilities.comments и capabilities.editing включены.
Таймер, вложения и виджеты отключены через capabilities.
Ядро не импортируется: types содержит локальный снимок общего контракта.

Списки задач для доски преобразуют REST-объекты `group` и `responsible` в строковые
подписи `name`. Пустой проект `{}` и отсутствующее имя дают пустую строку.
`taskDetail` сохраняет объект исполнителя: карточка использует его `id` и `name`.
Преобразование действует для всех ролей, включая задачи на приёмке.

Авторизация самодостаточна в src/auth.ts; импортов grigdesk-b24-discript нет.
Каждый сетевой запрос ограничен 30 секундами. Отказы REST сохраняют текст портала
без токена, пароля, CSRF и значений куки. Отказы прав и удалённая задача не повторяют
мутации, в том числе при HTTP 401 с явным кодом отказа прав.

## Комментарии и правка

`taskPageData(taskId)` читает `/rest/task.commentitem.getlist` с TASKID,
ORDER.ID=asc и start=0. Это официальное имя метода списка комментариев
([REST-документация][comments-list]).
Следующая страница берётся только из next ответа, без предположения о размере страницы.
Повторный или некорректный next завершает чтение ошибкой; одинаковые ID сворачиваются.
Нет искусственного ограничения числа страниц: пределы частоты и объёма задаёт портал.

Каждый комментарий преобразуется в mid, authorId, author, time, text, isSystem,
unread и attachments. AUTHOR_NAME сворачивается в имя, POST_DATE и POST_MESSAGE
сохраняются без изменения часового пояса и текста. REST не сообщает статус прочтения
и признак системного сообщения: unread и isSystem равны false. Вложения отключены,
поэтому attachments пуст. Маппинг написан в пакете; импортов discript нет.
Ошибка обсуждения пробрасывается в существующий маршрут вкладки комментариев;
`taskDetail` загружает задачу независимо и не обращается к обсуждению.

`addComment(taskId, text)` вызывает `/rest/task.commentitem.add` с TASKID и
FIELDS.POST_MESSAGE. Пустой текст отклоняется до сети. Возвращается `{ ok: true, commentId }`.
Автора определяет портал по авторизации; запись от имени другого пользователя не запрашивается.

`updateTask(taskId, input)` вызывает `/rest/tasks.task.update` с taskId и fields.
title, description, responsibleId и deadline переводятся в TITLE, DESCRIPTION,
RESPONSIBLE_ID и DEADLINE. Также принимаются groupId и priority, уже используемые
формой ядра. Возвращается `{ ok: true, id }` после подтверждения REST.
Отсутствующие поля и undefined не отправляются; пустое описание очищает описание,
deadline=null или пустая строка снимает срок. Никакого слияния с устаревшей карточкой нет.
Доступность срока в интерфейсе зависит от полей, передаваемых host: текущая HTTP-валидация
ядра допускает title, description, responsibleId, groupId и priority, но не deadline.
Пакет поддерживает deadline напрямую; ядро в рамках этого обновления не меняется.

Все три операции используют существующий транспорт: token передаёт auth в POST-теле,
password — cookie-сессию и sessid. В password разрешён только один повтор после явного
отказа сессии или анонимного HTTP 401, с новым входом, куки и CSRF. Сетевые сбои,
лимиты REST, отказы прав и ошибки задачи не запускают повтор мутации.

## Проверки пакета

Проверки запускаются из checkout GrigDesk через tests/run-node-tests-safe.sh,
с --test-concurrency=2 и NODE_TEST_MAX_RSS_MB=4096, передав tests/*.test.js пакета.
Все ответы эмулируются: проверяются оба режима, страницы и пустое обсуждение,
добавление, частичная правка каждого поля, отказы прав и удалённая задача,
неповторение мутаций при сбоях и ротация сессии при добавлении комментария.
